# План датасету для навчання AI-агента з гідрології

**Версія**: 1.0 | **Дата**: 2026-06-11
**Мета**: перетворити знання, накопичені пайплайном GeoHydroAI (3,6K+ статей, knowledge graph, NumericFacts, ChromaDB), на тренувальний датасет, після навчання на якому AI-агент коректно відповідає з гідрології, дистанційного зондування повеней, гідравлічного моделювання та суміжних дисциплін — **з опорою на докази, без фабрикації**.

## 3. Типи прикладів (8 task-сімейств)

### T1. Грунтований QA по фактах KG (~30–50K прикладів)
Згенеровані з трійок Neo4j шаблонами + перефразування LLM, **відповідь завжди підкріплена evidence-чанком**.

> *Q: "Які супутникові сенсори найчастіше використовують для картування повеней методом порогування SAR?"
> A: на основі агрегації Paper→USES_SENSOR + USES_METHOD, з цитуванням 3–5 конкретних статей (автор, рік, DOI).*

### T2. Numeric-fact QA (~10–15K)
З NumericFacts: "Який NSE отримала модель SWAT у дослідженні X для басейну Y?" — відповідь = значення + одиниця + точна цитата речення-доказу. Вчить модель **не округлювати і не вигадувати числа**.

### T3. Entity extraction / NER (~15–20K)
Вхід: абзац секції; вихід: структурований JSON сутностей (satellites, DEMs, methods, rivers) — рівно той формат, що валідований judge'м. Тільки приклади з `confidence ≥ 0.85` або підтверджені judge.

### T4. Entity linking до онтології (~10K)
mention + контекст → `canonical_id`. Джерело: `data/normalized/` з `match_type ∈ {alias, exact, disambiguation}` (semantic — лише після валідації Фази 2.4). Включити hard negatives ("Planet" супутник vs планета; "SPOT" vs spot).

### T5. Класифікація study_type / task (~7K)
title+abstract+methods → закриті enum (ті ж, що в judge-промпті). Лейбли: judge-підтверджені.

### T6. Citation-контекст і синтез (~5–10K)
"Що відомо про застосування U-Net до Sentinel-1 у Південно-Східній Азії?" → синтез по 5–10 статтях з обов'язковими посиланнями. Це **головний формат відповіді агента** (узгоджено з принципом evidence-grounded synthesis).

### T7. RAG-grounded відповіді з відмовою (~5K + 2K negative)
Приклад = питання + 5 retrieval-чанків з ChromaDB + відповідь, що цитує тільки надані чанки. **Обов'язкові негативи**: питання, на які наданий контекст НЕ відповідає → еталонна відповідь "у наданих джерелах цього немає". Вчить агента відмовлятися, а не галюцинувати.

### T8. Табличне/формульне розуміння (~3–5K)
З semantic_annotations: markdown-таблиця → інтерпретація; LaTeX-формула (Manning, Saint-Venant, NSE) → пояснення змінних. Обмежено 180 Nougat-статтями + GROBID-таблицями.

## 4. Схема прикладу (JSONL)

```json
{
  "id": "t2_numeric_000421",
  "task_family": "numeric_fact_qa",
  "messages": [
    {"role": "system", "content": "You are a hydrology research assistant. Answer only from evidence; cite sources; say so when evidence is insufficient."},
    {"role": "user", "content": "What NSE did the SWAT model achieve for the Desna basin calibration in Smith et al. 2021?"},
    {"role": "assistant", "content": "Smith et al. (2021) report NSE = 0.78 for the calibration period (2010–2015) of the SWAT model in the Desna basin [doi:10.xxxx/yyyy]."}
  ],
  "evidence": [
    {"paper_id": "sha256:...", "doi": "10.xxxx/yyyy", "chunk_id": "..._chunk_42",
     "quote": "The calibrated SWAT model achieved NSE of 0.78...", "section": "results", "page": 7}
  ],
  "provenance": {
    "generator": "kg_template_v1 | llm_paraphrase(model=...)",
    "source_confidence": 0.92, "judge_validated": true,
    "license_tier": "abstract_only | fulltext_oa | metadata_only"
  },
  "split": "train"
}
```

Ключові рішення: messages-формат (сумісний з SFT будь-якого провайдера); `evidence[]` обов'язкове поле — приклад без доказів **не потрапляє** в датасет; `license_tier` — див. §6.

## 5. Контроль якості (узгоджено з принципами проєкту)

| Правило | Механізм |
|---------|----------|
| Жодної фабрикації метрик/фактів | джерело кожного числа — NumericFact з evidence-цитатою; назва метрики тільки якщо вона є в тексті доказу (чинний принцип no-metric-fabrication) |
| Confidence-фільтр | сутності лише з `confidence ≥ 0.85` АБО judge-accepted; решта — у "сірий" пул для пізнішої ручної перевірки |
| LLM-перефразування ≠ LLM-знання | LLM дозволено перефразувати питання/відповідь, але всі факти у відповіді звіряються назад із evidence (automated entailment-check проти quote) |
| Діапазонна валідація | кожне число проходить metric_ontology range-check (після Фази 2.1) |
| Дедуплікація | exact + near-dup (MinHash по нормалізованому тексту відповіді); одна стаття не може породити >N прикладів одного сімейства (захист від домінування) |
| Анти-leakage спліт | спліт **по статтях, а не по прикладах**: всі приклади однієї статті в одному спліті; test-статті виключені з RAG-контекстів train; gold set (Фаза 2.4) → тільки eval |
| Баланс | стратифікація по task_family, study_type, географії (корпус має географічний bias — задокументувати розподіл у datasheet) |

## 6. Ліцензійні обмеження (критично, часто ігнорується)

Корпус містить статті Elsevier та інших видавців із закритими ліцензіями. **Не можна** включати повні тексти не-OA статей у датасет, що поширюється або використовується для тренування поза fair-use контуром.

- `metadata_only` — назва/автори/рік/DOI/цитування: безпечно для всіх статей.
- `abstract_only` — короткі цитати-докази (1–2 речення) + абстракти: прийнятний ризик для внутрішнього використання; для публікації датасету — перевірити окремо.
- `fulltext_oa` — повні чанки тільки для статей з OpenAlex `is_oa=true` + ліцензією CC-BY/CC-BY-SA (поле вже є в enriched-даних!).

Кожен приклад отримує `license_tier`; експортер вміє зрізати датасет до публікованого підмножини одним прапорцем.

## 7. План реалізації (нові модулі — `src/training/`)

Дотримання інваріанту проєкту: **окремий етап, не змішаний** з парсингом/HTTP/Neo4j-записом; читає тільки готові артефакти.

| Етап | Модуль | Зміст | Обсяг |
|------|--------|-------|-------|
| D1 | `src/training/sources.py` | readers поверх paper_json/normalized/enriched/NumericFacts/Neo4j/ChromaDB (read-only) | 2 дні |
| D2 | `src/training/generators/{kg_qa,numeric_qa,ner,linking,classification}.py` | T1–T5 шаблонні генератори (без LLM) — перші ~60K сирих прикладів | 4–5 днів |
| D3 | `src/training/generators/{synthesis,rag}.py` | T6–T7 з LLM-перефразуванням + entailment-перевіркою проти evidence | 4–5 днів |
| D4 | `src/training/quality.py` | дедуп (MinHash), range-check, confidence-фільтр, license_tier, спліт по статтях | 3 дні |
| D5 | `src/training/export.py` + CLI `python -m src.training.export --tier abstract_only` | JSONL + datasheet (статистика, баланси, версія) у `data/training/v1/` | 2 дні |
| D6 | Eval harness: held-out статті + gold set; метрики: factual accuracy проти evidence, citation precision, refusal correctness (T7-негативи), порівняння fine-tuned vs RAG-baseline | 3–4 дні |

**Разом: ~3 тижні** після завершення Фази 2 remediation-плану.

## 8. Стратегічна примітка: fine-tune чи RAG?

Чесна порада: для фактологічної точності по конкретних статтях **RAG залишиться кращим за fine-tune** — числа і цитати мають жити в індексі, не у вагах. Тому цільова архітектура агента: **fine-tune на T3–T7 для *поведінки*** (формат екстракції, дисципліна цитування, вміння відмовитись, термінологія домену) + **RAG поверх ChromaDB/Neo4j для *фактів***. Датасет за цим планом свідомо тренує поведінку, а T7-сімейство — саме інтерфейс між моделлю і retrieval. Один і той самий датасет також прямо придатний для евалюації будь-якої сторонньої моделі перед використанням у проєкті.
