# 12 — Сервер-каталог: посилання на праці та короткий аналіз

**Дата**: 2026-10-09 · **Стан**: план; нічого не зроблено.

**Рішення користувача (2026-10-09)**: усе перенести неможливо. На сервері мають бути **лише посилання на праці та короткий аналіз**.

**Що це замінює**: повний перенос із [09_MIGRATION.md](09_MIGRATION.md) (≈ 45–92 GB, GPU, Chroma, Neo4j) **не робиться**. Важка система лишається на робочій станції як «фабрика». Сервер отримує з неї малий **знімок-публікацію**.

```text
Робоча станція (фабрика, як зараз)                    Сервер (вітрина)
PDF · GROBID · Nougat · Ray · Ollama                  PostgreSQL (≈ 50 MB)
Chroma v2 · Neo4j · Postgres (шар правди)   ──export──▶  catalog.*  (лише читання)
data/ (≈ 90 GB)                             одностор.   малий API/сторінка
```

## 1. Що є на сервері

### 1.1 Посилання на працю (одна картка = одна праця)

| Поле | Звідки (вже є) |
|---|---|
| `paper_id`, `title`, `year`, `venue`, `publisher` | `core.paper`, `data/analytics/papers.parquet` |
| `doi` → `https://doi.org/…` | `core.paper.doi` (4 765 з 5 599) |
| `openalex_id` → `https://openalex.org/…` | `core.paper.openalex_id` (4 316) |
| OA-посилання (`oa_url`), якщо є | кеш OpenAlex (`biblio.http_cache`) |
| автори (скорочено), `cited_by_count` | `authors.parquet`, `papers.parquet` |

**Праці без DOI й без OpenAlex** (≈ 830) отримують лише бібліографічний запис. Посилання на PDF **ніколи** не публікуються: частина корпусу не з OA-джерел.

### 1.2 Короткий аналіз (структурований, без повних текстів)

| Блок | Звідки | Обсяг |
|---|---|---|
| Тип дослідження, країна/басейн | `papers.parquet` (`study_type`, `primary_country`) | — |
| Методи, сенсори, метрики, теми (канонічні ID + назви) | `normalized_entities` / `methods`, `sensors`, `metrics`, `topics` parquet | 223 методи, 98 сенсорів, 506 тем |
| Ключові числові результати (метрика = значення, одиниця, сторінка) | `numeric_facts.parquet` (24 884 факти) | лише топ-N на працю, з `confidence` |
| Рівняння (кількість + перелік відомих законів) | `law_links`, `formulas.parquet` | без LaTeX за замовчуванням |
| Коротке резюме, 2–3 речення | **немає — треба згенерувати** (див. D2) | ≈ 5 600 × ≈ 400 символів |
| Позначка перевірки | `verify.current` (ваші ручні перевірки) → «перевірено людиною» / «модельна оцінка» | — |

### 1.3 Чого на сервері немає

PDF, TEI, paper.json, Nougat-регіони й кропи, ChromaDB, Neo4j, GROBID, Ollama, Ray, моделі HF, кеші, матеріали статей (`paper_*`), повні тексти й анотації.

**Оцінка розміру**: ≈ 5 600 карток × ≈ 5–8 KB ≈ **30–50 MB**. Опційно один вектор на працю (768 × float32 ≈ 17 MB). Сервер — найменший VPS: 1–2 vCPU, 2 GB RAM, 20 GB диска. GPU не потрібен.

## 2. Як це влаштовано

1. **Експорт на фабриці**. Новий модуль `src/export/catalog.py` (`python -m src.export.catalog --out data/exports/catalog_<дата>/`) збирає картки з Postgres + analytics parquet у:
   - `papers.parquet`, `paper_entities.parquet`, `paper_facts.parquet`;
   - `manifest.json` з версією, кількостями, sha256 і git-комітом.

   Тільки читання сховищ: XML, OpenAlex HTTP і Neo4j-записи тут не змішуються (інваріант CLAUDE.md).
2. **Схема на сервері**: окрема БД `catalog` з таблицями `catalog.paper`, `catalog.paper_entity`, `catalog.paper_fact`, `catalog.release`. Шар правди (`core`, `verify` тощо) **не копіюється**, туди потрапляють лише похідні поля.
3. **Публікація**. `scripts/publish_catalog.sh` копіює знімок (rsync/scp кількох файлів) і завантажує його в нову схему `catalog_<версія>`. Після перевірок перемикається view або search_path, тож оновлення атомарне, а відкат — повернення на попередню версію.
4. **Доступ**: малий read-only сервіс. Варіанти: FastAPI з 3 ендпоінтами (`/papers`, `/papers/{id}`, `/search?q=`) або статична сторінка, згенерована з parquet. Пошук — Postgres full-text за назвою, сутностями й резюме; без Chroma.
5. **Оновлення**: після кожного інжесту на фабриці → `export` → `publish`. Напрям лише один: сервер ніколи нічого не пише назад.

## 3. Фази

| Фаза | Що | Критерій |
|---|---|---|
| 1 | Узгодити склад картки (D1–D3); зробити макет 5 карток вручну з експорту | ви погоджуєте вигляд |
| 2 | `src/export/catalog.py` + тести на фікстурах (без живих сховищ) | детермінований експорт: два запуски → той самий sha256 |
| 3 | Резюме (якщо D2 = так): пакетна генерація лише з власних полів картки, без нових фактів; заморожений файл `summaries_<версія>.parquet` | вибіркова перевірка 30 карток вами |
| 4 | Сервер: VPS, Postgres, read-only сервіс, TLS / Tailscale, щоденний `pg_dump` | `/health`, 20 контрольних карток ідентичні знімку |
| 5 | `publish_catalog.sh` + атомарне перемикання версій | повторна публікація того ж знімка нічого не змінює |

Для цього **не потрібно** розв'язувати 22 жорсткі шляхи, переносити Chroma чи Neo4j. Код фабрики лишається, де є. На сервер іде лише код вітрини: малий пакет або окремий репозиторій.

## 4. Відкриті рішення

| # | Питання | Рекомендація |
|---|---|---|
| D1 | Сервер публічний чи приватний (Tailscale)? | **Приватний спочатку**. Публічний — лише після перевірки ліцензійних питань щодо резюме й фактів |
| D2 | Коротке резюме: генерувати (Gemini/Ollama) чи лише структурована картка? | Спершу **структурована картка** (усе вже є, нічого не вигадується). Резюме — другим кроком, з позначкою «модельне» |

| D4 | Чи потрібен на сервері семантичний пошук? | Ні на старті (full-text). Якщо потрібен — один вектор на працю в pgvector, ≈ 17 MB |
| D5 | Праці-посилання (≈ 48 тис. процитованих, яких немає в корпусі) показувати? | Ні на старті; лише 5 599 праць корпусу |
