## 1. Де ми зараз

### Правда про поточний стан

Система GeoHydroAI опрацювала 3692 наукових статті про гідрологію. Ось що насправді відбувається:

```
Що система ДУМАЄ, що вона робить:
  3692 papers → extract NSE/RMSE/KGE → build knowledge graph

Що вона НАСПРАВДІ робить:
  3692 papers → parse XML → extract NSE: 0 results → build incomplete KG
                                         ^^^
                                     КРИТИЧНИЙ БАГ
```

**Факти, які важко прийняти:**

| Що вимірюємо | Що очікуємо | Реальність |
|---|---|---|
| Вилучення NSE (Nash-Sutcliffe Efficiency) | ~60-70% статей | **0%** |
| Вилучення супутникових даних | ~80% згадок | **27%** |
| Завантажений онтологічний словник | 11 файлів | **6 з 11** |
| Nougat GPU-обробка → pipeline | підключено | **відключено** |
| Розуміння формул | є | **відсутнє** |

**Оцінка довіри**: 6.8/10 (офіційна), ~4.5/10 (реальна)

### Де знаходиться головний баг

```python
# src/pipeline/pipeline.py, рядок ~472
# ПРОБЛЕМА: тільки abstract + results розглядаються для метрик
metric_text = (
    paper.get("abstract", "") + " " +
    paper.get("results", "")
    # ВІДСУТНЄ: + paper.get("methods", "")  ← ТУТ 100% NSE/RMSE
)
```

NSE, RMSE, KGE — це метрики *ефективності методів*. Вони завжди знаходяться в розділі **Methods**, а не Results. П'ять рядків коду → 0% вилучення.

## 2. Лабораторний журнал

### Метафора, яка пояснює все

Уявіть, що ви лаборант, якому треба архівувати 3692 наукових статті. У вас є два підходи:

**Підхід A: Один великий звіт (поточний стан)**

```
Стаття → [Ти читаєш все] → Один файл "paper_summary.json"
                                    ↓
                        {
                          "title": "...",
                          "methods": "...",
                          "metrics": [],  ← ПУСТО (баг)
                          "everything": "flat_text"
                        }
```

**Підхід B: Лабораторний журнал з артефактами (SODB)**

```
Стаття → [Різні спеціалісти] → Окремі лабораторні записи
           ↓                          ↓
    Структуроліст         formulas/   ← Кожна формула — окрема картка
    (GROBID)             tables/      ← Кожна таблиця — окрема картка
    Текстовий OCR        figures/     ← Кожна фігура — окрема картка
    (Nougat)             regions/     ← Кожен регіон — окрема картка
    Числовий аналіз      numeric_facts/ ← Кожен NSE — окрема картка
                                ↓
                    "Звіт" генерується з картками
                    будь-коли, будь-якою системою
```

**Ключова різниця**: В підході B — якщо один спеціаліст помиляється, решта не губиться. Можна переробити тільки один розділ. Є ланцюжок довіри від KG до оригінального PDF-пікселя.

## 3. paper.json — чому його недостатньо

### Що таке paper.json зараз

```json
{
  "paper_id": "2023_Smith_HydroModel",
  "title": "Comparative Analysis of Flood Models",
  "abstract": "We compare HBV and VIC models...",
  "sections": [
    {"title": "Methods", "text": "2000 words of plain text..."},
    {"title": "Results", "text": "1500 words of plain text..."}
  ],
  "entities": ["HBV", "VIC", "NSE"],
  "metrics": []
}
```

### Шість причин, чому це недостатньо

**1. Формула втрачає структуру**
```
У PDF:    E[η] = Σᵢ (Qobs,i - Qsim,i)² / Σᵢ (Qobs,i - Q̄obs)²

У paper.json:  "text": "NSE formula... E eta equals sum..."
                                 ↑ 
                    LaTeX розпався в plain text
```

**2. Таблиця стає плоским текстом**
```
У PDF:
┌─────────┬──────┬──────┬──────┐
│ Station │ NSE  │ RMSE │ KGE  │
├─────────┼──────┼──────┼──────┤
│ Rhine   │ 0.87 │ 12.3 │ 0.91 │
│ Danube  │ 0.79 │ 18.7 │ 0.84 │
└─────────┴──────┴──────┴──────┘

У paper.json: "Rhine 0.87 12.3 0.91 Danube 0.79 18.7 0.84"
                ↑
        Структура рядок-стовпець зникла
```

**3. Провенанс зникає**
```
KG-вузол: (NSE:0.87 {paper:"Smith_2023", station:"Rhine"})
              ↑
   Звідки це взялося? Яка таблиця? Яка сторінка? Яка клітинка?
   У paper.json — НЕВІДОМО.
```

**4. Інкрементальне переопрацювання неможливе**
```
Виявили баг у вилученні NSE?
→ Треба перегенерувати ВСЕ: XML-парсинг + NER + вбудовування + KG
   (навіть якщо XML-парсинг і NER були правильні)
```

**5. Паралельні парсери несумісні**
```
GROBID → paper.json (format A)
Nougat → окремий JSON (format B, відключений)
Docling → ? (format C, майбутнє)

Немає спільної мови між парсерами.
```

**6. GPU-результати Nougat відкидаються**
```
Nougat обробляє регіон (8 секунд GPU) → JSON в data/nougat_regions/
process_paper.py читає paper.json ← НЕ ЧИТАЄ nougat_regions/

GPU час: витрачено. Результати: ігноровані.
```

## 4. SDOM — модель документа

### Що це таке

SDOM (Scientific Document Object Model) — це **спільна мова** для всіх парсерів. Як HTML DOM для браузерів: будь-який браузер може рендерити будь-який HTML, тому що є стандарт.

```
Без SDOM:                          З SDOM:
                                   
GROBID → формат A                  GROBID ──┐
Nougat → формат B                  Nougat ──┼──→ TEIDocument → будь-який
Docling → формат C                 Docling ─┘    (спільна модель)  consumer
                                   
Кожен consumer треба              Один consumer, три парсери
адаптувати під кожен парсер
```

### TEIDocument — серце SDOM

```python
@dataclass
class TEIDocument:
    paper_id: str
    title: str
    sections: list[Section]      # ← Структуровані розділи
    formulas: list[Formula]      # ← Формули зі збереженим LaTeX
    tables: list[Table]          # ← Таблиці зі структурою рядків/стовпців
    figures: list[Figure]        # ← Фігури з підписами
    references: list[Reference]  # ← Цитати з метаданими
    
    parser_kind: ParserKind      # ← ХТО розібрав (GROBID/NOUGAT/HYBRID)
    parser_capabilities: frozenset[ParserCapability]  # ← ЩО вміє парсер
    markdown_text: str | None    # ← Nougat markdown (якщо є)
    visual_text: str | None      # ← Відновлений текст (якщо є)
```

### Що вміє кожен парсер

```
                STRUCTURE  COORD  REFS  FORMULAS  TABLES  OCR  MARKDOWN
GROBID              ✓        ✓      ✓      ✗         ✓      ✗      ✗
Nougat              ✓        ✗      ✗      ✓         ✓      ✓      ✓
Hybrid(G+N)         ✓        ✓      ✓      ✓         ✓      ✓      ✓
Docling (майб.)     ✓        ✓      ✗      ✓         ✓      ✓      ✗
```

**GROBID**: Знає *де* що знаходиться (координати), знає посилання. Не може читати формули.  
**Nougat**: Читає формули ідеально (LaTeX). Не знає координат.  
**Hybrid**: Найкращий з обох — GROBID дає координати, Nougat дає зміст.

## 5. SODB — база наукових об'єктів

### Концептуальна модель

SODB — це **персистентне сховище наукових об'єктів** у форматі Parquet, організоване по статті. Аналогія: якщо TEIDocument — це RAM (тимчасова робоча пам'ять під час обробки), то SODB — це жорсткий диск (постійне зберігання результатів).

```
data/sodb/
├── {paper_id}/
│   ├── .sodb_manifest.json     ← Що вже оброблено і коли
│   ├── regions.parquet          ← Всі семантичні регіони PDF
│   ├── formulas.parquet         ← Всі формули з LaTeX
│   ├── tables.parquet           ← Всі таблиці зі структурою
│   ├── figures.parquet          ← Всі фігури з підписами
│   ├── numeric_facts.parquet    ← Всі числові факти (NSE=0.87...)
│   └── chunks.parquet           ← Семантичні чанки для RAG
```

### Manifest — паспорт стану обробки

```json
{
  "paper_id": "2023_Smith_HydroModel",
  "pipeline_hash": "sha256:a3f7...",
  "stages": {
    "grobid_parse":    {"status": "done", "at": "2026-05-18T10:23:00"},
    "region_extract":  {"status": "done", "at": "2026-05-18T10:24:00"},
    "nougat_infer":    {"status": "done", "at": "2026-05-18T10:31:00"},
    "formula_extract": {"status": "done", "at": "2026-05-18T10:32:00"},
    "table_extract":   {"status": "done", "at": "2026-05-18T10:32:00"},
    "numeric_facts":   {"status": "done", "at": "2026-05-18T10:33:00"},
    "kg_sync":         {"status": "pending"}
  }
}
```

**Що це дає**: При переобробці (наприклад, виправили баг у вилученні NSE) — система перезапускає тільки стадії починаючи з `numeric_facts`. GROBID, Nougat (дорогий GPU!) не перезапускаються.

### Чому Parquet, а не JSON або SQLite

```
JSON:    Гнучкий. Але: без схеми, без типів, повільна аналітика.
SQLite:  Транзакційна. Але: один файл на всю базу → конкурентні записи.
Parquet: Колонковий. Типізований. Партиціонований. Сумісний з DuckDB/Pandas.
         Ідеальний для аналітики (SELECT metric, AVG(value) FROM ...).
         Кожна стаття — окремий файл → паралельний запис без блокувань.
```

## 6. regions.parquet — контракт між шарами

### Найважливіший файл у системі

`regions.parquet` — це **точка з'єднання** між парсинговим шаром і шаром вилучення. Без нього всі компоненти системи — острови.

```
╔══════════════════════════════════════════════════════════════╗
║                    ПАРСИНГОВИЙ ШАР                           ║
║  GROBID: координати       Nougat: зміст                      ║
║  (де знаходиться регіон)  (що містить регіон)                ║
╚══════════════════════╤═══════════════════════════════════════╝
                       │
                       ▼
              ┌─────────────────┐
              │ regions.parquet │  ← КОНТРАКТ
              │                 │
              │ region_id       │  ← UUID кожного регіону
              │ paper_id        │
              │ page            │
              │ bbox_x0..y1     │  ← координати від GROBID
              │ region_type     │  ← FORMULA/TABLE/FIGURE/TEXT
              │ nougat_text     │  ← зміст від Nougat
              │ nougat_latex    │  ← LaTeX якщо формула
              │ confidence      │
              │ crop_path       │  ← шлях до вирізаного зображення
              └────────┬────────┘
                       │
                       ▼
╔══════════════════════════════════════════════════════════════╗
║                    ШАР ВИЛУЧЕННЯ                             ║
║  FormulaExtractor  TableExtractor  FigureExtractor           ║
║  NumericFacts      ChunkBuilder    KGSynchronizer            ║
╚══════════════════════════════════════════════════════════════╝
```

### Що відбувається без regions.parquet

```
Зараз:
NougatRegionPipeline → data/nougat_regions/{paper_id}.json
                                    ↑
                          НІХТО НЕ ЧИТАЄ ЦЕЙ ФАЙЛ
                          process_paper.py → paper.json (ігнорує nougat_regions)

Результат: GPU рахує 8 секунд на регіон. Результат — у кошик.
```

## 7. Nougat — чому він змінює все

### Що таке Nougat технічно

Nougat — це нейромережа (Swin Transformer + mBART), яка перетворює **зображення сторінки** в **розмічений текст**. Розроблена Meta AI спеціально для наукових PDF.

```
Традиційний OCR:           Nougat:

Зображення → букви        Зображення → структурований LaTeX

"E n = 1 - S S r e s"     "$$E_n = 1 - \frac{\sum(Q_{obs} - Q_{sim})^2}
                                              {\sum(Q_{obs} - \bar{Q}_{obs})^2}$$"
      ↑                              ↑
  Незрозуміло              Машинозрозуміло
```

### Чому формули критичні для гідрології

NSE (Nash-Sutcliffe Efficiency) — центральна метрика в гідрологічному моделюванні:

```
E_n = 1 - SS_res / SS_tot

де:
  SS_res = Σ(Q_obs,t - Q_sim,t)²   ← сума квадратів залишків
  SS_tot = Σ(Q_obs,t - Q̄_obs)²    ← загальна дисперсія

Якщо E_n = 1.0 → ідеальна модель
Якщо E_n = 0.0 → модель не краща за середнє
Якщо E_n < 0   → модель гірша за середнє
```

Без розуміння цієї формули система не може:
- Порівнювати моделі між собою
- Ранжувати підходи за ефективністю
- Будувати довіру до числових фактів

### Nougat Pipeline: як це повинно працювати

```
PDF-сторінка
     ↓
GROBID: "На сторінці 5, координати [120,340,480,390] є формула"
     ↓
Вирізати регіон (з контекстним розширенням ±35px)
     ↓
Nougat inference: 8 секунд GPU
     ↓
"$$E_n = 1 - \frac{SS_{res}}{SS_{tot}}$$"
     ↓
Зберегти в regions.parquet + formulas.parquet
     ↓
Нікуди більше НЕ треба звертатися до GPU для цієї формули
```

### L1 Кеш — чому це рятує 17 днів GPU

```
Без кешу:
  3692 статті × ~54 регіони/стаття × 8 сек = 442 годин = 18.5 днів GPU

З L1 кешем (95% hit rate при повторних запусках):
  Ключ: SHA256("{model}:{version}:{crop_image_sha256}")
  Промах: 8 секунд GPU
  Влучення: 2 мілісекунди читання з диску
  
  Перший запуск:     442 годин
  Другий запуск:     442 × 0.05 = 22 годин
  Третій запуск:     22 × 0.05  = 1.1 години
```

## 8. Провенанс — ланцюжок довіри

### Навіщо це потрібно

Уявіть: система каже "Модель HBV досягає NSE=0.87 на річці Рейн". 

Науковець запитує: "Це з якої статті? З якої таблиці? Це вимірювання чи передбачення? Який часовий проміжок?"

Без провенансу — відповіді немає. З провенансом:

```
Neo4j вузол:
  (NSE:0.87 {basin:"Rhine", model:"HBV"})
       ↓ fact_id: "fact_abc123"
       
numeric_facts.parquet:
  fact_id="fact_abc123" | source_region_id="reg_xyz789" | confidence=0.94
       ↓ source_region_id
       
regions.parquet:
  region_id="reg_xyz789" | page=7 | bbox=[120,340,480,390] | crop_path="..."
       ↓ crop_path
       
data/crops/2023_Smith/page7_region42.png  ← ОРИГІНАЛЬНЕ ЗОБРАЖЕННЯ
       ↓ посилання
       
GROBID TEI XML: координати в пікселях оригінального PDF
       ↓
PDF: байти 1,234,567 — 1,245,890
```

Будь-який KG-вузол можна **трасувати до пікселя оригінального PDF**.

### Чому це важливо для наукового контексту

У гідрологічному KG одне значення NSE=0.87 може означати дуже різні речі:

```
NSE=0.87 при калібруванні (на тих самих даних, що й навчання) — завищене
NSE=0.87 при валідації (на нових даних)                       — справжнє
NSE=0.87 для щоденного кроку часу                             — одне значення
NSE=0.87 для річного кроку часу                               — зовсім інше
```

Без провенансу ці значення змішуються в KG. З провенансом — кожен факт несе свій контекст.

## 9. Чому розділення стадій критичне

### Поточний стан: Монолітний god-object

```
pipeline.py (2148 рядків, 87 функцій)
├── XML парсинг (повинен бути в GROBID шарі)
├── GeoNames lookup (повинен бути окремим актором)
├── NER (SpaCy actor — правильно)
├── Embedding (SPECTER2 — правильно)
├── Вилучення NSE з plain text (повинно читати numeric_facts.parquet)
├── Запис в Neo4j (повинен бути окремим synchronizer)
├── Запис в ChromaDB (повинен бути окремим synchronizer)
└── Генерація paper.json (повинна бути assembly step)
```

**Проблема**: При зміні будь-якої частини треба перезапустити все. При бозі — неможливо тестувати ізольовано. При помилці в KG-записі — всі попередні кроки ідуть в смітник.

### Цільова архітектура: Конвеєрні стадії

```
Stage 1: PARSE
  Input:  PDF
  Output: regions.parquet, formulas.parquet, tables.parquet
  Tools:  GROBID + Nougat (через cache)
  
Stage 2: EXTRACT  
  Input:  regions.parquet (читає тільки це)
  Output: numeric_facts.parquet, chunks.parquet
  Tools:  TableExtractor, FormulaExtractor
  
Stage 3: ENRICH
  Input:  numeric_facts.parquet + external APIs
  Output: enriched_facts.parquet + entities.parquet
  Tools:  OpenAlexActor, GeoNamesActor
  
Stage 4: ASSEMBLE
  Input:  всі parquet файли
  Output: paper.json (читабельний summary)
  Tools:  PaperAssembler
  
Stage 5: SYNC
  Input:  paper.json + numeric_facts.parquet
  Output: Neo4j вузли + ChromaDB записи
  Tools:  KGSynchronizer, VectorSynchronizer
```

**Ключова властивість**: Кожна стадія читає з попередньої і пише в наступну. Стадії не знають одна про одну напряму. При помилці в Stage 5 — Stage 1-4 не перезапускаються.

## 10. Дорожня карта

### Що треба зробити в порядку важливості

## Висновок

GeoHydroAI — це система з правильними компонентами, з'єднаними неправильно. Є GROBID, є Nougat, є TEIDocument, є NumericFact, є Neo4j. Але вони — острови.

**SODB** — це міст між ними: спільний контракт даних у форматі Parquet, де кожен компонент пише в свій шар і читає з попереднього. `regions.parquet` — це перший і найважливіший міст.

Перший крок — найпростіший і найважливіший: виправити 5 рядків у `pipeline.py:~472` і отримати NSE від 0% до ~60%. Решта — архітектурна еволюція, яка будується поверх цієї основи.
